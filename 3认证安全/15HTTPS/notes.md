## 一、知识点讲解

### 1. HTTPS 与 TLS

HTTPS 是 HTTP 通过 TLS 安全连接传输。TLS 在 HTTP 数据到达网络前提供安全保护；应用通常使用 HTTP 的请求与响应语义，不需要自己逐段加密 JSON。

TLS 的三个核心安全属性：

- **机密性（confidentiality）**：旁观者截获传输流量时，不能直接读出受保护的应用数据。
- **完整性（integrity）**：传输数据遭到未授权修改时，接收方能够检测并拒绝它。
- **身份认证（authentication）**：客户端验证连接对端是否持有与目标服务身份绑定的密钥。

HTTPS 不只等于加密。网站即使证书有效，业务仍可能出错、存在漏洞或具有欺骗性；TLS 保护通信连接，不替应用判断业务是否可信。

### 2. 证书、CA 与服务器身份

服务器证书把服务身份（通常是域名）与公钥关联起来。证书由 CA 签名；客户端根据本机信任的根证书验证签发链。访问网站时还要核对：

1. **主机名**：证书身份覆盖用户请求的域名。
2. **有效期**：当前时间处于证书有效期内。
3. **信任链**：证书可以验证到客户端信任的 CA。
4. **私钥持有证明**：服务器在握手中证明自己持有证书公钥对应的私钥；仅复制公开证书不能冒充服务器。

任何验证失败都应中止连接或显示证书错误。有效证书只证明连接身份符合验证结果，不证明网站经营者善意或业务结果正确。

### 3. 非对称密码学与会话密钥

- 证书中的公钥和服务器保管的私钥参与服务器身份认证。服务器用私钥完成握手签名证明，客户端用证书公钥验证。
- TLS 通过密钥协商建立本次连接的共享秘密，并据此导出连接使用的流量密钥。
- 后续应用数据使用对称密钥保护，适合高效处理大量数据。

记忆方式：**证书/私钥帮助确认身份并参与握手；会话密钥保护后续数据。**

> TLS 1.3 精确说明：现代握手通常用 ClientHello 和 ServerHello 中的临时 `key_share` 进行 (EC)DHE 密钥协商，而不是用证书公钥直接加密整份 HTTP 内容。Certificate 给出证书链，CertificateVerify 用证书私钥对握手 transcript 签名，Finished 确认握手和派生密钥。双方完成 Finished 后进入受认证加密保护的应用数据阶段。练习里的握手列表是教学用概念顺序，不是 TLS 1.3 的精确逐消息时序。参考 RFC 8446。

### 4. 握手与 TLS 终止

概念流程：

```text
客户端与服务器协商 TLS 参数、密钥材料
服务器提供证书及握手身份证明
客户端验证服务器身份
双方确认握手，得到应用数据所需的密钥
通过 TLS 连接安全传输 HTTP 数据
```

生产部署中，TLS 常在 Nginx、云负载均衡器或托管平台终止：外部连接使用 HTTPS，代理再把请求转发给 FastAPI。代理到应用之间是否继续加密，取决于部署网络和配置。

“SSL 证书”是常见历史叫法；现代安全连接使用 TLS，SSL 已淘汰。

**问题 A：把 JavaScript 的 `!` 用在 Python**

```python

```

Python 的逻辑否定运算符是 `not`。用户按提示改成 `not expired`。

**问题 B：将所有失败归为主机名错误**

最初写成一个复合条件：所有条件通过才返回 `accepted`，其余情况都返回 `hostname_mismatch`。因此不受信任和过期证书错误地落进同一分支。

按规定验证顺序改为独立检查：主机名不匹配 → 不受信任 → 已过期 → 接受。修正后，正常、三种单独错误和多项错误优先级测试全部通过。

代码 Review 后把三层嵌套改为 guard clauses，减少缩进并直接表达验证顺序。

## 五、本章结论

- HTTPS 是 HTTP over TLS；TLS 提供机密性、完整性和服务器身份认证。
- 客户端检查证书中的服务身份、有效期、信任链，并验证服务器持有对应私钥。
- 现代 TLS 握手协商连接密钥并认证服务器；应用数据随后用对称流量密钥保护。
- HTTPS 保护连接和传输，不保证站点业务正确或可信。
- 后端部署常在反向代理或负载均衡器终止 TLS；代理与 FastAPI 之间的保护由配置决定。
