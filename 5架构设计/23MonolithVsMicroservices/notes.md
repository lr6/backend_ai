## 一、知识点讲解

### 1. 本质定义

微服务不是一个「技术」，是一个**部署形态**。

| | Monolith（单体） | Microservices（微服务） |
|---|---|---|
| 部署单位 | 一个应用，全量上线 | 每个服务单独上线 |
| 数据 | 共用一个库，可以直接 JOIN | 各管各的库，不能 JOIN |
| 调用 | 函数调用（进程内、纳秒级、一定成功） | 网络调用（毫秒级、会超时、会失败） |

**三条判据（判断是不是微服务）：**

1. **能独立部署**（最硬的一条）
2. **有自己的数据库**，别人不能直接读你的表
3. **服务之间只能走网络**（HTTP / 消息队列），不能 import 对方代码

### 2. 分布式单体（Distributed Monolith）

只满足「独立部署」、不满足「独立数据」的形态：多个进程，但共用一个库、改动仍要一起发版。

> **既背了拆分的全部成本（网络、部署、联调），又保留了单体的全部约束。两头坏处都占，优点一个没有。**

极端版本叫 **nanoservice（纳米服务）**：服务拆得比一个类还小。

### 3. 数据边界是拆分最难的部分

单体一条 SQL：

```sql
SELECT u.username, COUNT(t.id)
FROM users u LEFT JOIN todos t ON t.user_id = u.id
GROUP BY u.id, u.username;
```

拆开后（users 归 auth-service，todos 归 todo-service）：

```python
# 1. 只查自己的库
rows = db.execute(select(Todo.user_id, func.count()).group_by(Todo.user_id)).all()
ids = [r[0] for r in rows]

# 2. 一次批量请求拿名字（不是循环里单条请求！）
users = httpx.get(f"{AUTH_URL}/users", params={"ids": ",".join(map(str, ids))}).json()

# 3. 内存拼装
name_by_id = {u["id"]: u["username"] for u in users}
result = [{"username": name_by_id.get(uid), "count": n} for uid, n in rows]
```

**为什么不能 JOIN：**

- 技术上：跨 PG 实例，SQL 无法 JOIN
- 设计上（更重要）：能直接读别人的表 ⇒ 表结构变成事实上的公共 API ⇒ auth-service 改表要先问 todo-service ⇒ 「独立演进」作废

**N+1 换了个位置**：

| 单体 | 微服务 |
|------|--------|
| 懒加载：1 次查用户 + N 次查 todo | 循环里 `httpx.get`：1 次聚合 + **N 次 HTTP** |
| `selectinload`：IN 批量一条 | 批量接口 `?ids=1,2,3` |

网络层更可怕：本地 SQL 微秒级，跨机 HTTP 毫秒级，还多了超时和失败。

**四种绕法：**

| 手法 | 怎么做 | 代价 |
|------|--------|------|
| API 组合 | 调批量接口，内存拼装 | 多一次往返，对方挂你就挂 |
| 数据冗余 | 存一份副本，改名时发事件同步 | 最终一致 |
| 读模型（CQRS） | 用事件维护查询专用表 | 架构再复杂一层 |
| BFF 层 | 前端专用聚合层调多个服务 | 多一个服务要维护 |

「共用一个只读从库」= 主动放弃数据边界，退化成分布式单体，只能过渡期短期用。

### 4. 新常态：最终一致

冗余方案下用户改名后，todo 列表可能短暂显示旧名字，靠事件追平。

> **同一份数据出现在两个地方，允许短暂不一致。** 单体里没有这个问题，因为数据只有一份。

两个方案的取舍（一致性 vs 可用性）：

- **A 实时调接口**：auth-service 挂了名字拿不到（可用性被绑定）；还多一跳延迟 → 要加本地缓存 + 降级（「未知用户」）
- **B 冗余副本**：改名后短暂旧名字 → 要处理事件丢失（对账 / 定时全量同步）

### 5. 微服务真正解决的问题（组织问题，不是代码问题）

| 问题 | 单体 | 微服务 |
|------|------|--------|
| 团队协作 | 30 人一个仓库，抢发版、天天冲突 | 各团队独立上线 |
| 独立扩缩容 | 只有下单吃 CPU 也得整机复制 | 只扩 order-service |
| 故障隔离 | 通知模块内存泄漏 → 整进程挂 | 通知挂了下单照常（要防级联 → Circuit Breaker） |
| 技术选型 | 全公司一个框架 | 搜索 ES、日志 MongoDB |

**Conway's Law**：系统架构会长成组织架构的样子。微服务的本质是「让部署边界 = 团队边界」；组织没变大，拆的动机就不成立。

**成本（微服务税）：** 网络（超时/重试/幂等/熔断）、数据（不能 JOIN/最终一致/分布式事务）、运维（N 套部署日志监控）、调试（请求穿过 5 个服务要 trace id）、本地开发（起 6 个容器）。

> 第五、六阶段后面大半内容（Circuit Breaker、structlog、Prometheus、K8s、Rate Limiting）本质都是给微服务税擦屁股的。

### 6. 什么时候拆

**成立的信号（都是「部署边界挡了谁」）：**

- 团队发版互相阻塞、合并天天冲突
- 局部需要独立扩缩容
- 局部需要独立故障隔离
- 独立合规/安全域（支付单独审计）
- 业务边界天然清晰（认证 vs 订单本来就无共享逻辑）

**不成立的信号：**

- ❌ 代码太乱 → 该拆模块
- ❌ 想换新技术/新语言 → 单体也能换
- ❌ 显得架构先进 → 面试话术
- ❌ 怕以后拆不动 → 先做模块化单体，边界画对随时能拆

**演进路径（练习会考的顺序）：**

> **Modular Monolith（模块化单体）→ 边界稳定 → Strangler Fig 绞杀式抽取 → 绝不大爆炸重写**

绞杀者模式：新服务并排跑，流量一点点切过去，旧代码一块块摘掉。

### 7. 怎么拆：纵向，不横向

**错误示范（按技术层横切）：**

```
api-gateway-service / controller-service / service-service / dao-service
```

问题：一个「创建 Todo」请求 = 4 次跨网络调用。

| 问题 | 表现 |
|------|------|
| 延迟累加 | 4×RTT |
| 可用性相乘 | 99.9%⁴ ≈ 99.6% |
| 事务做不了 | 创建要跨服务协调回滚 |
| 发版又耦合 | 加个字段 3 个服务一起改一起发 ⇒ 回到全量部署 |

**根因：把「分层」当成了「边界」。** Controller/Service/DAO 是同一块业务内部的三层，天然一起变；按层切等于把一个人劈成三段还指望他自己走路。

**正确做法（按业务能力纵向切）：**

```
auth-service    ← 内部 controller + service + dao + 自己的 users 表
todo-service    ← 内部 controller + service + dao + 自己的 todos 表
notify-service  ← （需要时才建）
```

分层没有消失，变成每个服务内部的私事。

**前端类比：** 微前端按「用户模块 / 订单模块」拆，不是按「所有页面 / 所有组件 / 所有 store」拆。订单模块要显示用户名，不能直接读用户模块的 Pinia store，只能调它的接口或存副本。

**判断边界最好用的尺子：**

> **谁经常一起变，就放一起；谁从来不一起变，才值得拆。**

拆分理由 = 业务能力独立 + 数据所有权独立 + 变更原因不同 + 能独立发版。
（「各自有 dao/controller/service」**不是**理由——每个服务内部都会有，那是结果不是依据。）

### 8. 基础设施 ≠ 服务

- **Redis / PostgreSQL** 是基础设施，不在服务计数里；「N 个数据库」指逻辑上各管各的表，物理上可以是同实例不同 schema
- **Nginx** 是反向代理，也不是服务
- **uvicorn 进程 + Celery worker 进程 = 进程隔离 ≠ 微服务**：共享同一个仓库、`models.py`、数据库，改一处仍全量部署。它解决「不阻塞请求」，不解决「独立演进」

> 判断只认两件事：**代码库是不是一个、部署单位是不是一个。**

### 补充提问（练习完成后，用户主动问）

> 「练习 2 的 `layer_kinds = {"controller", "service", "dao"}` 是啥，元组吗？`any` 是什么玩法」

**这是第 2 次在容器字面量上卡住**（第 14 项 CORS 问过「`not in` 后面一会 `()` 一会 `{}`」），说明 `tuple / list / set / dict` 的括号形状还没焊死。

| 写法 | 类型 |
|------|------|
| `[a, b]` | list |
| `(a, b)` | tuple |
| `{a, b}` | **set** |
| `{"k": v}` | dict |
| `{}` | **dict**（坑！空 set 只能 `set()`） |

- 用 set 的理由：成员判断 `x in set` 是哈希查找 O(1)，`x in list` 是逐个比 O(n)
- `any(iterable)` = JS 的 `Array.prototype.some()`；短路，第一个真就停
- `all(iterable)` = JS 的 `Array.prototype.every()`
- 空集合语义：`any([])` → `False`，`all([])` → `True`
- `for x in xs` 外套 `()` 是**生成器表达式**（惰性、边算边喂），不是 tuple
- 练习 2 读法：「任一服务的 responsibility 在 `{controller, service, dao}` 里 → 返回 `["horizontal_split"]`」；`services` 为空时 `any` 返回 `False` → 返回 `[]`（没有服务就没有横切问题）

用户检查题回答：空集合写 `set()` ✅、`any([])` 返回 `False` ✅。

## 四、踩坑速查

| 错误认知 / 写法 | 正确认知 | 关联知识点 |
|----------------|---------|-----------|
| 代码拆成多个文件就是微服务 | 判据是独立部署 + 独立数据库 + 网络通信 | 三条判据 |
| 「因为每个服务都有独立 dao/controller/service，所以拆」 | 每个服务内部都会有这三层，这是结果不是依据 | 纵向 vs 横向拆分 |
| 按 controller / service / dao 各拆一个服务 | 把一个人劈成三段；nanoservice | 分层 ≠ 边界 |
| 多个进程共用一个库 = 微服务 | 分布式单体，两头坏处都占 | 分布式单体 |
| uvicorn + celery worker + nginx = 微服务架构 | 进程隔离/基础设施，仍是一个代码库 | 基础设施 ≠ 服务 |
| 代码太乱 → 上微服务 | 拆模块（Modular Monolith） | 拆分信号 vs 伪信号 |
| 微服务是给代码质量开的药 | 是给组织/部署问题开的药 | Conway's Law |
| 循环里逐个调远程接口 | 批量接口一次拿，内存拼装 | 分布式 N+1 |
| 远程数据缺失直接抛异常 | `.get(id, 默认值)` 降级 | 可用性 |
| 事件处理器每次新建列表、不幂等 | 原地写同一值，重复消费结果不变 | 幂等（连 Celery acks_late） |
| 一上来就拆微服务 | Modular Monolith → Strangler Fig 逐步抽 | 演进路径 |
| `{"a", "b"}` 当元组用 / 空 `{}` 当空集合 | `{}` 是 dict，空 set 写 `set()`；元组是 `()` | 容器字面量（第 2 次卡住） |
| 不知道 `any(...)` 是什么 | `any` = JS `some()`，短路；`all` = `every()`；`any([])`=False、`all([])`=True | 内置函数 |
| 以为 `any(x for x in xs)` 外面是 tuple | 那是生成器表达式，惰性求值 | 生成器表达式 |
